# Edge function rules

- All AI calls go through the Lovable AI Gateway on its current default chat model with reasoning enabled; function tools are sent through the Responses endpoint via the shared `supabase/functions/_shared/aiResponses.ts` helper (stateless: every call resends its input with `store:false`), because the gateway's chat-completions endpoint serves text generation only.
- The live interview chat (ai-interview-chat, conversation turns only) asks the gateway for the lowest reasoning effort it accepts (none, then minimal, then low) because a person waits for every reply, and its first message is a fixed greeting sent without calling the model; evaluation, co-pilot and all other AI calls keep reasoning_effort low.
- Administrator notification emails use credential-free pg_net event callbacks and service-only atomic claims with bounded retries and managed idempotency; only stored notification content and the administrator's own address may be sent, without new queues or schedules.
- Send payout approval emails from the dedicated authenticated payout notification function after the existing status RPC succeeds, deriving recipient, money and date server-side and deduplicating by payout ID; email failures must not undo financial actions.
- Scheduled and database-woken job functions (consultant-profile-reminder, assignment-reminders, responsiveness-run, consultant-policy-run, availability-run, referral-run, bulk-messages-run) refuse any call without the private `x-job-token` header from `public.job_invoke_headers()`, checked only by `_shared/jobAuth.ts`; every cron command or pg_net wake-up (including re-applied docs/sql files) must send those headers, so outsiders cannot trigger e-mails or sends. Behind that check, safety lives in the service-only claim RPCs plus repeat-call guards (profile reminders 30 minutes), and responses contain counts only.
- Assignment request reminders follow the same job-token pattern with a 4-minute sweep guard (below the 5-minute schedule so Critical reminders are not held back); timings and due rules live in `_shared/assignmentPolicy.ts`, mirrored by the claim RPC, so popup, e-mails, client card and tests agree.
- Consultant responsiveness (Feature M) is computed only in the database from arrival-time events (availability checked when a request arrives); `_shared/responsiveness.ts` mirrors the rules for display, ranking and tests, and the responsiveness-run sweep follows the same job-token pattern with an 8-minute guard, so cards, ratings and ranking never compute official statistics in the browser.
- Consultant Service Policy notices (consultant-policy-run) follow the same job-token sweep pattern with the shared 30-minute guard; acknowledgement state and grace rules live only in the database (mirrored by `src/lib/consultantPolicy.ts` for display), so pop-up, banners, e-mails and restrictions agree. The notice mail is always bilingual (preferred language first, each version complete, rendered under the Gmail clip limit with a compact second policy as fallback) and carries the full published text and live settings numbers, laid out only by `_shared/consultantPolicyEmail.ts` through createElement (React escaping, tested in vitest) and rendered in one piece via the template's `html`/`text` hooks, because streamed rendering splits Arabic letters.
- Admin user management (admin-manage-user, admin-send-invitation) checks the caller with `admin_can` (falling back to the admin / super admin role until the prepared SQL is applied), requires a reason for sensitive actions, rate limits per admin and records every change through `um_record_state` with actor, target, before, after and reason; bulk runs are capped at 200 with a dry run first.
- Notification pauses (Feature Q) have one gate, the SQL `notifications_paused`: e-mail reaches it through `sendTemplateEmail`'s `pause` option (`notification_email_check`, which also decides the signed footer), in-app/popups through the notifications insert trigger (`silent` / `held_until`); signed links are made and checked only with `_shared/notificationPause.ts` (HMAC with the `NOTIFICATION_PAUSE_SECRET` environment secret) and handled only by the credential-free `notification-pause` function, so essential notices can never be paused by one path and not another. Footers never carry our own unsubscribe link: the managed e-mail footer owns unsubscribing.
- Admin bulk messages (Feature R) go only through the bm_* database functions (audience, exclusions, messages.send, caps) and the job-token-checked `bulk-messages-run` worker (service-only throttled bm_claim/bm_finish, counts-only responses) for in-app and Telegram; bm_arm_worker schedules it only while a campaign is due or sending and removes it after drain, so idle days cost nothing; e-mail is never a bulk channel and admin-notification-email skips their notice types, because app e-mails must stay one-recipient and event-triggered.
- Owner test sends of the policy notice use only the super-admin consultant-policy-test-send function (fixed owner recipient, "[TEST] " subject prefix via sendTemplateEmail's subjectPrefix, 6 per hour) and write no notice log, notification or acknowledgement, so tests never reach or count against consultants.
- In-app feedback (Feature U) is submitted only through the `feedback` function into the service-only `submit_feedback` RPC (user id from the verified token, visitors as a salted IP hash, magic-byte image checks, random names in the private `feedback` bucket); browsers never write the feedback tables, submitters read only through `my_feedback`, and the shared `_shared/feedback.ts` mirrors the database limits and masking so dialog, function and SQL agree.
- Confirmation e-mails link to /auth/confirm only while the published site serves `public/auth-confirm-ready.json` (probe in `_shared/authConfirmLink.ts`), otherwise the original link; any function change that links to a new front-end page needs the same kind of marker check, so e-mails never point at an unpublished page.
- Feature Y e-mails (availability-run) are job-token-checked and event-driven: the database queues them in availability_email_queue and wakes the function through pg_net only while e-mails wait (no schedule); the service-only claim RPC leases rows (10 minutes, 5 attempts), the first availability notice and the hold-ended notice are essential, administrator reminders use the reminders pause category, and the recurring availability reminder is only the Urgent block inside the daily profile reminder mail.
- Ticket meetings are created only by the authenticated schedule-meeting function (caller = admin, the ticket's client or a verified assigned consultant, checked in code; session written with the service role so database guards still run); external attendees (max 10, validated by _shared/meetingInvite.ts) get one invitation each linking the public /join page and the public meeting-ics file (neutral title, scheduled sessions only), because app e-mails cannot carry attachments and the sessions insert policy only covers the client with an assigned consultant.
- Feature Z referral e-mails (referral-run) follow the Feature Y pattern: the database queues one row per event in referral_email_queue and wakes the function through pg_net only while e-mails wait; the service-only claim RPC leases rows (10 minutes, 5 attempts); first-reward and bank-detail-change notices are essential, reminders/acknowledgement requests use the reminders pause category and the rest the activity category.
- Knowledge-based interview questions: document text is untrusted and reaches the model only as `_shared/untrustedText.ts` excerpts (local ids, no titles, injection-like excerpts dropped) and drafts pass its validator (schema, slot module, allowed sources, no 10-word copy, not asked before); drafting uses the cheapest current zero-retention chat model within the per-interview call cap, key points stay in interview_plans, and sap_doc_* is never a question source (admin preview links only).
- Referral e-mails (referral-run, referral-email-test) render only through `_shared/referralEmail.ts` via the referral-notice template's html/text hooks; the banner is a published-site file probed with HEAD before use, and test sends go only to the caller's own confirmed address with the [TEST] subject prefix (sendTemplateEmail subjectPrefix), writing no queue, notification or referral row.
- Speech-to-text goes only through the signed-in `voice-transcribe` function (complete 16 kHz WAV checked by `_shared/voiceAudio.ts`, minutes claimed atomically by the service-only voice_claim_segment, SAP hints and spelling fixes only from `_shared/voiceGlossary.ts`, settings from `_shared/voiceSettings.ts`); audio is never stored unless the admin setting is on, and logs carry status codes only, so caps, privacy and vocabulary behave the same for every microphone.
