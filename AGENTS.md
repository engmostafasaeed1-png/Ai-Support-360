# Architecture rules

Subdirectories have their own `AGENTS.md` (e.g. `supabase/functions/`, `docs/sql/`); read it before changing files there.

- Payout reminders are shared by dashboard and Earnings; admin readiness badges use presence/status metadata only, keeping bank identifiers out.
- Dimmed buttons use Button `reason` (keys and server codes in `src/lib/blockedReasons.ts`) or `busy`, never bare `disabled` (guard test; `disabled-ok:` opt-out), so each block says why and what next.
- Shared Button drops its variant gradient when callers pass a base background colour (custom gradients kept), preserving emergency/status colours.
- Consultant landing/pricing pages own head tags via useHeadTags (dedupe, restore on unmount), never also via RouteSeo, to avoid competing updates.
- Admin full consultant profiles load only via the audited admin-only RPC in the shared sheet (ephemeral queries, short-lived links, timed in-memory bank reveals), so private payout data is never persisted.
- Invoice details use shared billing controls + admin confirmation hook.
- Timesheet PDF/CSV rows come only from the shared timesheet document helpers (screen amounts, approval metadata), so exports never diverge.
- Credibility scores/star fills come only from the shared credibility library; photo performance rings only from lib/ringAvatar via ConsultantRing (map popups via its DOM twin), outer arc pure client rating, inner arc only public responsiveness, so all surfaces agree.
- Consultant request/success counts and Success levels come only from the database success RPCs (aggregates only, no per-ticket data) and lib/successLevel, shown through the shared ring summary as SuccessStars level stars (never a ring arc), so every surface agrees and the AI-interview tier never shares its wording.
- Weekly availability, grace exclusion, reminders and holds are decided only in docs/sql/availability-hold.sql (hold_* functions, time-based consultant_on_hold), mirrored by _shared/availabilityRules.ts; 'on_hold' is set only by holds, so status, directory, matching and reminders agree.
- Brand artwork uses shared CDN logo pointers; portal-menu public links are `external: true` (new tab).
- The consultant Profile page is the single editor (no duplicate setup tab); legacy onboarding links land there.
- Rank consultants only with the shared deterministic matcher (`supabase/functions/_shared/ticketMatch.ts`: hard filters, admin-tunable weights, why-chips) everywhere, incl. directory sort; client blocks are exclusions, favourites an optional capped criterion; displays derive from its weights; AI writes text only, so rankings stay reproducible.
- Ticket payment terms and consultant invoices are written only via SECURITY DEFINER RPCs; a client-approved invoice becomes a pending payments row so existing billing handles collection.
- Keep client bid comparison/deadline rules in the shared client bidding library and client mutations in useClientBids so ticket tabs and lists agree.
- Share embedded profile guide visibility and the existing completeness result through one provider; reuse wizard guide content so the active editor and interview anchor stay consistent without duplicate scoring or guide copy.
- Consultant field visibility/required state comes only from admin field rules via useProfileFieldRules (FieldGate/RequiredMark), except hard-required country/city enforced by the shared consultant location helpers and server grace checks; client lists drop hidden_consultant_ids (show everyone if that call fails), so one rule applies everywhere without blocking saves.
- Founding Consultant awards live in a separate read-only badge table with locked server-only allocation and audited admin RPC overrides; optional feature queries fail closed until the user applies the prepared SQL, so existing consultant queries and private profile access remain unchanged.
- Profile autosave uses loaded baselines, immutable snapshots and readiness gating; sensitive fields stay manual (no empty writes or audit floods).
- AI interviews start only through the shared interviewStart resolver (resume in-progress, else reuse newest pending, single-flight insert) behind a visible blocker/preflight; completion counts the interview as its own weighted item from the shared helper, and evaluation confirms trigger-awarded badges, so no surface creates duplicates or a different percent.
- Long ticket submits and matching runs use the shared TaskProgressPanel with real step states; new tickets save via ticketSubmission helpers (single-flight, tab-stored id) so progress stays honest and tickets never duplicate.
- Team engagement: on gated tickets only team activation writes active assignments and tickets.consultant_id, after all four gates, for client- and admin-added members (admin changes audited); team requests only invite and team rows only mirror existing tables, so access rules follow the gates.
- Social sign-in starts only via startSocialSignIn (rechecks settings); index.html head tags carry `data-rh="true"` so Helmet replaces them.
- Others' consultant names come only from the database viewer rule and the shared consultantName formatter, so no screen, e-mail or AI text leaks a hidden name.
- Realtime uses `subscribeWhileVisible` with row filters (whole tables only on admin pages); portals and Arabic load lazily, cutting DB/bundle load.
- Meetings are created only by the schedule-meeting function; entry points use ScheduleMeetingButton/Launcher with `_shared/meetingSchedule.ts`, so disabled buttons show why and screen and server agree.
- Scroll rules live only in ScrollToTop/lib/scrollUtils; landing reveals use lib/reveal (hides only what it marks), so content shows without scripts.
- Sign-up confirmation links open /auth/confirm, verifying only on a button press (code fallback) so scanners cannot use them up; expired links show ConfirmLinkProblem, never the social error.
- Consultant referrals (Feature Z): attribution, activation, fraud signals, rewards and referral payouts are decided only by docs/sql/referral-program.sql triggers; the browser reads only via my_referral_* / admin_referral_* RPCs (masked, default-deny) and `src/lib/referrals.ts` mirrors the rules (threats/tests: docs/referral-security.md), so money is never set from a screen.
- The Refer & earn "Programme rules" hub builds all screen and PDF text only through `components/referral/rules/rulesContent.ts` from live settings (admin notes are plain-text settings), and checklist/journey/simulator math lives only in `src/lib/referralRules.ts`, so no programme number is hard-coded and screen, PDF and tests agree.
- App RPC helpers call the database only through lib/safeRpc (real Promise, never rejects); never chain .catch() on a query builder (ESLint no-restricted-syntax + src/test/noCatchOnSupabaseBuilder.test.ts), because builders have no .catch() and it crashes the page.
- Refer & earn page tracking (reward lines, payouts, rejected referrals, terms status, menu dot) is read only through the own-data RPCs in docs/sql/referral-tracking.sql and grouped/filtered only by `src/lib/referralTracking.ts`, so the page never computes money and shows no ticket title or hourly rate.
- Refer & earn invitations are decided only by docs/sql/referral-invitations.sql + notice-channels.sql (eligibility, dedupe, caps, kill switch, idempotent send, audit) and sent only as a Feature R campaign (in-app, push, Telegram), with channel choices from `src/lib/sendChannels.ts` and `src/lib/referralInvitations.ts` mirroring the rules, so no screen sends outside server rules.
- Notice pop-ups open only for kinds in `src/lib/noticeModalConfig.ts` via useNoticeQueue + NoticeModal (one slot, "1 of N", optimistic close, guards/retries in `src/lib/noticeGuard.ts`); stored text only via `src/lib/noticeText.ts`, so routine notices never block and closed ones never re-open.
- Referral in-app notices keep type 'referral' and get kind, colour and deep link only from `src/lib/referralNotice.ts` (database titles); referral e-mail layout rules live in `supabase/functions/AGENTS.md`.
- The admin referral Dashboard reads only the administrators-only `admin_referral_dashboard` aggregate (docs/sql/referral-dashboard.sql) and only reshapes it in `src/lib/referralDashboard.ts`; forecast parts (already earned, 3-month trend, approved-unpaid work) stay separate and labelled, so no screen invents or blends programme money.
- Platform e-mail sender identity (display name, From local part on the verified aisupport360.com, own-domain Reply-To/contact) comes only from `_shared/emailSender.ts` + docs/sql/email-sender.sql settings with default fallback; non-registered people are never e-mailed by the platform (consultants use own-mailbox mailto/app sharing), so deliverability and consent rules hold.
- Refer & earn invitation effectiveness is counted only by docs/sql/referral-invite-tracking.sql (signed-in click tracking + admin counts) from links tagged only `from=invite&ch=<channel>` by `src/lib/inviteTracking.ts`; no pixels, tokens or personal data in links, so e-mail opens are never measured.
- Every microphone uses the shared useVoiceRecognizer (server transcription with automatic browser fallback, paused while the AI speaks) via VoiceInput or the hook; dictation fields pass `value` so spoken text is appended once, and answer quality is logged only through lib/voice/voiceMetrics (no text), so recognition and metrics stay consistent.
- Voice learning (suggestions, vocabulary versions, routing, consented audio, question stats) is decided only in docs/sql/interview-voice-learning.sql, mirrored by `_shared/voiceLearning.ts`, `voiceRouting.ts`, `questionQuality.ts`; browsers send only filtered word pairs/error counts, never audio, and the provider model is never retrained.
- Ticket BRDs are read/written only via brd_* functions in docs/sql/ticket-brd.sql (brd_role_for = ticket-document readers + both-signed NDA; consultants see attached versions only) and the ticket-brd function for AI; the PDF (src/lib/brd/pdf.ts) is attached as ticket_documents doc_type 'brd', so generic document rules never expose a BRD.
- Ticket tracking: the automatic stage is derived only by deriveStage in `src/lib/ticketTracking.ts` from tt_facts (docs/sql/ticket-tracking.sql, reusing team_next_step/team gates) and never stored; the manual working status is written only by tt_set_working_status and never touches tickets.status, so SLA, success statistics and the official flow stay unchanged.
- BRD approval is decided only in docs/sql/ticket-brd-approval.sql (rounds bound to version + hash, append-only decisions, brd_gate_state for team gates, stage facts, timeline, work/timesheet/confirmation triggers), mirrored by `src/lib/brdApproval.ts`; its e-mails only via `_shared/brdApprovalEmail.ts`, so gate, screens and mail agree.

- Hideable pages (e.g. Solution Architecture) carry `visibleSetting` in navConfig and are filtered only via `src/lib/pageVisibility.ts` and guarded by PageVisibilityGate (admins may open); a missing switch counts as off, so hidden pages never leak.
- SLA policies are decided only in the database (docs/sql/sla-policies.sql: immutable versions and per-ticket snapshots, one business-minute clock function pair, reconcile/sweep in the breach job, idempotent reminders sent by sla-run) and mirrored by `_shared/slaPolicy.ts`; with the switch off the legacy SLA columns and notices are untouched, so screens, mail and tests agree.
- Support agreements are decided only by sa_* functions in docs/sql/support-agreements.sql (append-only records, crew gate sa_confirmation, SLA only while Active, files via sa_document_*, sa_sweep, tickets get ticket_rates source 'agreement'), mirrored by `_shared/supportAgreements.ts`, so pricing v2, invoices and payouts stay unchanged.
- NDA signing is decided only by docs/sql/nda-signature-identity.sql (append-only nda_signatures, ID numbers encrypted by the nda-signature function in nda_signatory_identity, logged admin reads) and mirrored by `_shared/ndaSignature.ts`; screens show the NDA only via NdaStatusCard/NdaSignDialog and legacy signatures stay valid, so gates never change.
- Partner portal: tenants.is_partner + partner_* RPCs only (docs/sql/partner-portal-mvp.sql) via src/lib/partnerPortal.ts, so no second org system.
