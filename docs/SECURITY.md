# Security model and operations

This document describes the security controls that protect the platform and the operational steps that cannot be expressed in code. Keep it up to date when you change any of them.

## 1. Defence in depth

| Layer | Control | Where |
|---|---|---|
| Identity | Supabase Auth; 12-character minimum password policy in the UI | `src/lib/passwordPolicy.ts` (Supabase Auth settings must match, see section 5) |
| Authorization (data) | Row-level security on every table plus `BEFORE INSERT/UPDATE` guard triggers that protect trust-bearing columns (verification status, ratings, AI scores, SLA fields, escrow, signatures, links) from mass assignment | `supabase/migrations/` |
| Authorization (functions) | Every edge function authenticates the caller; privileged operations check the role; service-role-only functions compare the bearer token to the service key in constant time | `supabase/functions/_shared/security.ts` |
| Input | zod validation, size caps, strict allow-lists (connection IDs, URLs, SSRF guard for integrations) | edge functions, `src/lib/remoteAccess.ts`, `src/lib/safeUrl.ts` |
| Abuse | Database-backed rate limits (`public.check_rate_limit`) on AI, e-mail, demo, logging and credential endpoints | `withinRateLimit` in `_shared/security.ts` |
| Secrets | Integration credentials are encrypted with AES-256-GCM (`v2:` HKDF format; legacy rows stay readable); every decrypt is written to the audit log | `_shared/credentials-crypto.ts` |
| Links | Links that come from data are opened through `openExternal` / `safeHref`; URL columns are validated by database triggers (`guard_url_columns`, `guard_path_or_url_columns`) | `src/lib/safeUrl.ts` |

## 2. Roles

- Self-service sign-up can only create `client` or `consultant`. `admin` and `super_admin` are never read from sign-up metadata.
- Grant the first super admin from the Supabase SQL editor (it runs as the owner and bypasses the guards):
  `insert into public.user_roles (user_id, role) values ('<user uuid>', 'super_admin');`
- Consultant verification is decided by admins on the Consultant approvals page, never by the consultant. Interview scores are written only by the `ai-interview-chat` function.

## 3. Edge functions

Secrets (Project settings, Edge Functions, Secrets):

| Name | Purpose |
|---|---|
| `CREDENTIALS_ENCRYPTION_KEY` | Master secret for credential encryption. Rotating it requires re-encrypting stored credentials. |
| `ALLOWED_ORIGINS` (optional) | Extra comma-separated CORS origins (production and preview domains are built in). |
| `SITE_URL` (optional) | Canonical site URL used in e-mailed links; default `https://www.aisapsupportnow.com`. |
| `INTEGRATION_EXTRA_ALLOWED_HOSTS` (optional) | Extra host suffixes for self-hosted Jira / ServiceNow / Zendesk instances (SSRF allow-list). |
| `ANYDESK_API_KEY` (optional) | Enables the admin-only AnyDesk directory. |

Notes:

- `send-transactional-email` accepts only the service-role key. Browsers must use purpose-built functions such as `demo-reschedule-notify`. The guard lives in a file generated by Lovable's e-mail set-up flow: after re-running that flow, verify that a call with the public anon key still returns 401/403.
- `auth-email-hook`, `process-email-queue` and `preview-transactional-email` are server-to-server endpoints (webhook signature, service key, platform key).
- `integration-webhook` requires the per-integration secret (at least 32 characters) in a header, or an HMAC signature. The secret is available to the integration owner in the integration settings.

## 4. Front-end and hosting

- The published site is served by Lovable hosting, which does not apply `public/_headers`. The effective protections are the `<meta>` CSP in `index.html` (no `unsafe-eval`) and `public/anti-clickjack.js`, which hides the app when it is framed by an origin that is not on the allow-list. `frame-ancestors` cannot be set through a meta tag.
- Next CSP step (needs a host or CDN rule that can send real headers): serve the CSP as a header with `frame-ancestors`, remove `'unsafe-inline'` from `script-src` and start with `Content-Security-Policy-Report-Only`.
- Set the primary domain in Lovable so that the canonical link injected into the static HTML matches `https://www.aisapsupportnow.com`.

## 5. Manual settings outside the code base

1. Supabase, Authentication, Password: minimum length 12, require upper/lower/digit/symbol, enable leaked-password protection.
2. Supabase, Authentication, Email: set the OTP / link expiry to 1 hour or less (the project currently reports 24 hours).
3. Supabase, Storage: keep `chat-files`, `nda-documents`, `ticket-documents`, `dispute-evidence`, `proposal-documents` and `business-process-docs` private.
4. Enable multi-factor authentication for every admin and super-admin account.
5. Review admin roles regularly: `select * from public.user_roles where role in ('admin','super_admin');`

## 6. Verifying the controls

```sql
-- SECURITY DEFINER functions callable by API roles (review every row)
select p.proname, pg_get_function_identity_arguments(p.oid) as args
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.prosecdef
  and (has_function_privilege('anon', p.oid, 'EXECUTE') or has_function_privilege('authenticated', p.oid, 'EXECUTE'))
order by 1;

-- Tables without row-level security (expect none)
select c.relname from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;
```

- Front-end unit tests: `npx vitest run src/lib`.
- Smoke test after every publish: sign up as a client and as a consultant, submit the landing-page demo wizard while signed out, open Remote access as a consultant, run an AI triage chat.

## 7. Reporting a vulnerability

Send security reports privately to the platform owner. Do not open public issues for vulnerabilities.
